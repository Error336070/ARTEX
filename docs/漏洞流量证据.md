# Multiple traffic evidence records for findings

Linked traffic in finding details supports selection across pages, roles and notes, ordering, and unlinking. The Traffic page can also link multiple records to one existing finding. Evidence inherited from another task is read-only; open the source task to edit it.

“Agent automatic traffic binding” in System settings is off by default. Read and update it through `agent_traffic_binding` at `/api/settings`. Enabling it increases token use for request/response inspection, tool calls and prompt instructions; agents use the setting on their next turn. When disabled, automatic binding parameters and the supplemental binding tool are hidden, automatic binding guidance is omitted, and new automatic bindings from existing sessions are rejected. Manual binding, traffic capture, reading saved evidence and export are unaffected.

When enabled, the default flow is: record a finding → automatically start the report agent → verify and bind traffic → write the report against the latest evidence version. The reporter preserves verification commands, key output, existing real traffic IDs and their roles in `evidence`. The report agent checks finding details and execution records with `traffic_search` / `traffic_get`, calls `bind_finding_traffic`, then reads the latest `version` before saving the report. With the setting disabled, the report agent receives no additional raw traffic search/read tools and performs no automatic binding; it can still read manually bound snapshots and generate reports.

Existing callers remain compatible: `traffic_refs` / `evidence_hint_id` in `report_finding` can still bind explicitly at submission. Binding is optional: for non-HTTP findings such as TCP issues, missing capture or no exact matching record, omit references and report normally. Preserve other verifiable evidence such as command output and logs; explaining the missing binding is recommended, with no new required field. Every submitted ID must be valid and have a complete body. Any failure rolls back the whole binding operation; failure of explicit binding during reporting rolls back the entire report submission. Adding the same snapshot again creates no duplicate binding and does not overwrite notes.

## Agent identifiers and report versions

`report_finding` adds optional parameters; array order determines the initial evidence order:

```json
{
  "traffic_refs": [
    {"traffic_id": "real-traffic-id", "role": "baseline", "note": "Normal account request"},
    {"traffic_id": "another-real-traffic-id", "role": "proof", "note": "Reproduction request"}
  ]
}
```

Roles are `baseline` (normal comparison), `proof` (finding proof), `verification` (additional verification), and `supporting` (supporting evidence, the default). Check real records with `traffic_search` / `traffic_get` first; domain and time only filter candidates and do not establish task ownership.

Prompt guidance references [CyberStrikeAI's finding reporting tool guidance](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go), adapted to this project's optional binding contract, without requiring an explanation when no traffic is attached. Never guess IDs or repeat probes solely to obtain an attachment.

The first return line remains `finding recorded: <exploration node ID>`; subsequent JSON provides the independent finding record `finding_id`, exploration node `finding_node_id`, and binding summary.

- `get_finding_traffic(finding_id)` takes the **independent finding record ID** and returns an ordered list and `version`. Supply `binding_id`, `side=request|response`, `offset` and `length` to read chunks of up to 8192 bytes.
- `finding_id` in `update_finding_report` **continues to mean the exploration node ID**. Set the new `evidence_version` to the version actually read. If evidence changes during generation, the stale write is rejected; reread and regenerate.
- Legacy report calls without a version do not claim to cover existing traffic evidence. Changes to bindings, notes, roles or order mark existing reports as needing an update.

When automatic binding is enabled, `add_hint` / `add_task_hint` can preserve `traffic_refs` in individual hints or each element of batch `hints`. A planner reporting on another agent's behalf may supply `evidence_hint_id` to select references from the corresponding hint in this task, but cannot reference inherited hints. The system never infers bindings from domain, time or browsing history. Failed submissions create no partial finding and do not start reporting early.

Use `bind_finding_traffic(finding_id, traffic_refs)` to attach missing evidence to an existing finding without registering it again. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` return explicit `finding_id` and `finding_node_id`; legacy `id` retains exploration-node semantics.

Startup only adds optional properties to older tool schemas and extends the original default traffic tool bindings to the report agent; the supplemental binding tool is assigned to the report agent by default. Custom binding lists, prompts, descriptions and enabled states are preserved. Guidance is added after final tool assembly: reporters hand over existing evidence; the report agent checks, binds and writes reports. Platform chat without task context should hand over structured hints to the task agent rather than reporting directly. Hand over existing evidence before declaring a task complete; missing traffic does not require waiting. Failed `report_finding` calls do not trigger the report agent.

## API

Base path: `/api/exploration/findings/{finding_id}/traffic`, using the independent finding ID. Existing authentication applies; `context_task` checks task visibility and inherited read-only access.

| Method / relative path | Request / response |
| --- | --- |
| `GET` | Ordered summary, evidence version, report evidence version |
| `POST` | `{"traffic_refs":[...]}` appends the full batch |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"Description"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`; must contain the complete list |
| `GET /{binding_id}` | Snapshot metadata and bounded body preview |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1` downloads the complete original bytes |

Version/order-set conflicts and writes during archiving return `409`; inherited writes return `403`; missing bindings or bindings outside the finding return `404`. Traffic/attachment reading and validation failures return explicit errors.

## Storage and migration

Startup migrates PostgreSQL idempotently: adds `traffic_evidence_snapshots`, `finding_traffic_bindings`, and `findings.evidence_version` / `report_evidence_version` (default 0). Historical text is never used to infer missing bindings.

Snapshots preserve the original traffic ID, capture time, URL, method, status, request/response headers, body lengths and SHA-256. Bodies are stored by hash at `<data>/evidence/blobs/<first-two-characters>/<hash>.bin`, independently of removable `data/traffic`; multiple findings can share snapshots/bodies. Snapshots have no content-update endpoint; integrity mismatches make reads and exports fail.

Read complete bodies under the original traffic write lock, including large-body blobs and legacy directory records. Persist and verify files first, then write exploration nodes, intent relationships, findings, snapshots and bindings in one PostgreSQL transaction; notify the planner only after commit. Failure may leave unreferenced files, but never partial business records.

PostgreSQL advisory lock `7337741004` coordinates evidence files and SQL references; task row locks prohibit evidence changes once archiving is queued. Restoration holds the evidence lock from body installation through metadata commit. Deleting a finding cascades to its bindings.

The cleanup job runs hourly and only reclaims unreferenced content outside active operations, with a minimum delay of 24 hours. Ordinary traffic cleanup never touches the evidence directory. Back up PostgreSQL and `data/evidence` together when backing up active data.

## Export and archives

Markdown includes an ordered evidence list and version; JSON includes metadata; CSV adds counts and binding IDs. `md-zip` preserves finding Markdown and includes:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown references messages through relative links. Before sending a download, copy attachments, verify hashes, compress, sync to disk, and read all ZIP entries to verify CRCs; missing or corrupt data fails the whole download. Full attachments preserve the original binary bytes.

Archive v3 gathers snapshots and bodies by finding bindings, independently of original traffic or domains. Active data is only cleaned after archive validation; shared evidence is retained. Restore validates and installs bodies first, then restores metadata and bindings transactionally, with retries supported. v1/v2 remain restorable; absent new fields are explicitly set to 0.

## Verification and limits

Use a separate, newly created PostgreSQL test database for each test package, selected with `ARTEX_PG_DSN`, to avoid residual task/model fixtures triggering background runs. Run complete relevant package tests and confirm none are skipped because configuration is missing:

```sh
# Set ARTEX_PG_DSN to the package's independent test database before each run; explicit configuration failures must raise errors.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

Frontend verification includes `npx tsc --noEmit`, Biome checks for affected files, a Webpack build, and `NEXT_EXPORT=1` static export. Use independent cache directories to avoid overwriting a running development service.

Local end-to-end acceptance uses independent ports, controlled HTTP / domain HTTPS targets, and temporary data directories. It covers both binding entry points, selection across pages, ordering/notes, errors, inherited read-only access, downloads, and export after original traffic deletion, archiving, active-body reclamation, restoration and hash verification.

The initial version uses a global evidence coordination lock; large binding/export batches or slow attachment downloads may make other evidence operations wait. Missing capture records or complete bodies cannot be fabricated. This feature changes neither capture settings nor certificate handling for direct HTTPS access to IP addresses.
